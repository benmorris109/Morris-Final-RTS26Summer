Project Overview

This project was developed as the final integration capstone for EEL4775 – Real-Time Systems. It is based on the previously completed Application 2 and demonstrates the design, implementation, and analysis of a real-time scheduling application using the ESP32 simulator on Wokwi. This project follows the theme of an industrial amusement ride control system and upholds this theme by tailoring task names and functions to commonly found tasks for a ride control system. It models the architecture of a ride control system by separating critical system functions into independent tasks with different execution rates and priorities. Rather than focusing on the complexity and functionality of the hardware, this project mainly looks at task execution, scheduling techniques, and timing predictability. These are fundamental concepts that are used in embedded control systems across many different fields, including themed entertainment engineering.

This application executes four periodic FreeRTOS tasks that are pinned to core 1 of the ESP32. The highest priority task performs a dispatch interlock check every 10 milliseconds to represent a safety-critical operation. A second task handles the motor speed control every 20 milliseconds, simulating the continuous process of ride motion. The next task is a lower-priority task that refreshes the operator display every 50 milliseconds. The lowest priority task executes every 100 milliseconds and records and logs maintenance information. Assigning these different priorities and execution periods allows the scheduler to ensure that time-critical operations preempt lower-priority background activities when it is necessary.

Core 0 of the ESP32 is reserved for system monitoring and interaction with the user. Depending on the selected configuration, the application will either output the task statistics through the serial monitor on Wokwi or it will host an HTTP server that displays the scheduling information through a web browser. By separating the monitoring functionality from the real-time control tasks, we can prevent background and diagnostic operations from interfering with the deterministic scheduling of the critical tasks. It also provides visibility into the system’s performance while it executes.

The main objective of this project is to validate that the design of this system satisfies real-time timing requirements. Worst-case execution times (WCET) were measured for each task rather than estimated, which can then be used to calculate processor utilization information. These measurements were used to evaluate the ride control system using Rate Monotonic Scheduling (RMS), Earliest Deadline First (EDF), and Response-Time Analysis (RTA). These statistics and calculations can be found in the README of the Wokwi project, some of which are mirrored in the GitHub README. Performing these analyses demonstrates that the selected task periods and priorities create a predictable execution pattern while meeting timing constraints under the measured workload.

Overall, this project demonstrates a practical application of real-time scheduling theory by relating it to an embedded ride control system. By combining periodic task design, fixed-priority scheduling, timing analysis, processor utilization measurements, and monitoring in a single application, the project illustrates many of the engineering principles required for a consistent embedded system. The architecture is representative of techniques and ideas that are used in safety-related control systems in the themed entertainment industry. This makes it a strong basis for future extensions such as interrupt-driven safety handling, sensor integration, network communication, and actual deployment on physical hardware.

System Features

Fixed-Priority Scheduling

Four periodic FreeRTOS tasks execute using fixed priorities to simulate a real-time industrial control application.

WCET Measurement

Worst-case execution times were measured directly on Wokwi and used for schedulability analysis.

Deterministic Timing

Each task executes at a defined period ranging from 10 ms to 100 ms while meeting its deadline.

Schedulability Analysis

Processor utilization was evaluated using RMS, EDF, and Response-Time Analysis.

Real-Time Monitoring

Execution timing and heartbeat information are displayed through the serial monitor and web dashboard.

Future Improvements

Throughout this course, I gained a much deeper understanding of how real-time embedded systems are designed, analyzed, and verified. Before taking this course, I had experience with writing embedded programs to produce a correct output, but I had not considered whether they could meet timing requirements. Learning about deterministic timing, worst-case execution time, processor utilization, and analysis changed how I view embedded software. I understand that in real-time applications, producing the correct result is only part of the desired goal, and the result must also be produced to meet strict deadlines.

This final capstone project brought together many of the concepts introduced throughout the semester into a single application. Designing multiple FreeRTOS tasks with different execution periods and priorities demonstrated how a scheduler works with workloads while ensuring critical tasks always execute first. Even though this project was based on Application 2, something we had previously completed, looking back on it and viewing it from a different light helped expand on the topics. Measuring the WCET of each task instead of estimating execution times showed the importance of using real data when evaluating system performance. Applying RMS, EDF, and RTA to the measured times connected the theoretical concepts from this class to the actual practical behavior of the system.

One of the more challenging aspects of the course was learning how different synchronization primitives fit together. While writing code, using the built APIs is simple, but understanding why one primitive should be used over another is complicated. Comparing these primitives forced me to consider latency, resource ownership, and scalability rather than just making the code function correctly. Something that was challenging about this specific project was measuring execution times and verifying scheduling behavior. This required much more analysis than I had initially expected, and it became clear that designing a real-time system involves a lot of analysis along with implementation.

If I were to complete this project again, I think I would spend more time planning the software architecture before writing code to execute it. During development I focused on implementing individual tasks first and working on the overall organization later. Creating more detailed designs earlier might have simplified the integration and reduced the amount of restructuring that I had to do towards the end of the project. Another thing I would do differently is actually expand upon the built system from application 2 by including some of the later concepts in the other applications. It would be interesting to integrate this onto physical hardware with actual sensors to see how the scheduling and timing analysis can be evaluated under practical operating conditions. I would also want to include interrupt-driven programming and using some of the synchronization primitives to make the system more complex and perform more functions.

The most valuable lesson I learned is that successful embedded projects are built on predictability and timing rather than just functionality. A program that works often is not sufficient for applications such as in ride control systems and other areas of the themed entertainment industry. Safety systems cannot be run this way on a major scale. Instead, engineers must demonstrate that software consistently meets strict timing requirements. Understanding how to measure WCET, analyze utilization, assign task priorities, and verify scheduling has given me a strong basis in real-time systems engineering. These are skills that extend beyond this course and are extremely valuable in future embedded projects and ride control systems.
